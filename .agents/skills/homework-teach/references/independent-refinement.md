# Independent refinement and incremental publication

The owner's completion target is **100/100 from independent Astra, followed by 100/100 from Claude Code Opus 5.5 at high effort**. Apply `docs/REVIEW-RUBRIC.md` unchanged: all 23 lesson categories and the separate reusable-process table. Score each lesson; assess linked sequence coverage as well. A high average cannot hide an incomplete lesson, unassessed category, or failed privacy, homework-separation, accuracy, or accessibility boundary.

## Fix a candidate and establish the baseline

Privately map the source's conceptual demands to the lesson or linked sequence. Visually inspect supplied diagrams and notation. Keep this comparison and source material outside the public checkout. Record the public candidate's HTML and dependency SHA-256 hashes, subject/shared skill hashes, rubric edition/hash, and declared scope. Keep those files fixed during review. Existing scores certify only their recorded artifacts and rubric edition; establish a current baseline before claiming improvement.

Give a fresh `gpt-6-astra` reviewer the raw requirements, rubric, exact candidate, authorized private source paths, and necessary verification tools. Use `fork_turns: "none"` with a self-contained brief; propagate this rule to every child. Both reviewers have read-only authority over the candidate: they may run checks and create temporary evidence outside the checkout, but may not edit, stage, publish, or change the scored artifacts. Verify hashes after review; unexpected mutation invalidates the assessment. The reviewer is independent of the author and receives no author's verdict, other reviewer's score, or pressure to award a target. It may choose its own investigation and must distinguish observed evidence from inference and report category scores, totals, findings, and limitations. Source-specific analysis stays private. The reusable process score is separate from the lesson scores.

## Astra loop

Correct demonstrated defects in the lesson and the skill that generated it. Re-exercise the revised skill on the same private input: regenerate the affected teaching sequence from those instructions, then compare it against the unmet requirements. A manually patched page alone does not validate the skill. Preserve sound original content and stable URLs while regenerating affected sections; check their integration with the whole lesson. Run affected behavior checks and freeze the new candidate. Obtain a fresh independent Astra assessment. Continue until both lesson and reusable-process scores are 100, with no unassessed category or unresolved hard boundary. Preserve actual evidence, including disagreements and lower scores; repeated grading of unchanged content is not an improvement strategy.

After two revisions that do not improve the unresolved assessment, or an explicit impasse, create a fresh independent brainstorming sub-agent. This trigger applies in either reviewer stage and when alternating reviewer requests prevent convergence. Give the raw task, current artifacts, demonstrated failures, and approaches already attempted. Require **at least three materially different untried approaches to the skill's teaching workflow**. Compare them against the outstanding rubric concerns, reconcile conflicting requests using evidence rather than averaged scores, choose the strongest supported option, explain the choice briefly, implement it in the skill and lesson, and return to independent Astra testing. A missing model, input, permission, or service is an access blocker, not a reason to brainstorm teaching changes or claim success.

For shared-skill edits, identify every registered subject whose generation decisions change. Re-exercise those decisions against authorized representative inputs, including the available subject corpus in the current run; check the produced teaching for regressions before publishing. Keep specialist guidance scoped when a finding is not shared. If representative private input is unavailable, record that scope as untested instead of claiming cross-subject execution. Instruction-level routing cases can be tested without inventing an assignment or publishing a fabricated lesson.

## Claude Code loop

Only after Astra reaches 100 on the fixed candidate, invoke the installed Claude Code CLI in a new session with exact model `claude-opus-5-5`, `--effort high`, and `--no-session-persistence`. Verify the actual model in the returned `modelUsage`; an alias or fallback is insufficient evidence. Use CLI help for supported options. Give Opus the same scope, rubric, frozen artifacts, and private source access, without Astra's scores or conclusions. Use read-only review tools and keep prompts, full output, extracted sources, and runtime evidence outside the public checkout. Do not disable permission enforcement to obtain a review.

Require category scores, totals, process score, specific findings, and evidence limits. Apply useful suggestions to the skill and lesson, then regenerate or re-exercise the affected teaching from the revised instructions and the same private input; a page-only patch does not test the skill. Any changed reviewed bytes invalidate prior certification of that candidate: return to Astra first, reach 100 there, then ask fresh Opus to assess the revised candidate. The same plateau/brainstorming rule applies here. Continue until **the same final candidate and its dependencies** have 100 from both. Never silently substitute a model or effort. If the requested reviewer is unavailable, preserve the work, report the exact blocker, and continue independent authorized work.

## Publish each better version

The owner authorizes incremental updates to the existing destination. Publish a fixed candidate when its active-stage independent score improves over that stage's baseline/best published score, or a separately scored reusable skill improves without a lesson regression. During Astra refinement compare Astra assessments; during Opus refinement compare Opus assessments and require renewed Astra 100. Scores from different reviewers are not interchangeable. Never replace a stronger published candidate with a regression. A tie with no demonstrated improvement does not justify publication merely to refresh a timestamp.

Before every push, complete semantic review, update truthful manifest attestations and exact hashes, rebuild the index, run `node scripts/check.mjs` and `node --test tests/*.test.mjs`, and exercise affected browser behavior/library navigation. Stage only explicit reviewed paths: lesson, skill, relevant dependencies, registry if changed, manifest, index, and sanitized review record. Inspect the staged diff and commit message for private data. Preserve existing URLs and the verified library route. Do not change email partitions as part of this review loop.

Record sanitized scores, reviewer/model/effort, candidate/dependency/skill hashes, relevant fixes, checks, and deployment status in the existing review record. Do not publish source comparisons or private paths. After pushing each improved version, verify the live lesson and library. An intermediate deployment remains an intermediate deployment; it must not claim dual-review completion. Infrastructure improvements may be published after their own independent process review and required checks while lesson refinement continues.

Completion requires both reviews on the final candidate, reviewed skill changes, passing required checks, and verified live delivery. Report unavailable checks or pending deployment honestly. Keep the pending stage and evidence pointers in the existing task record when interrupted; a status request or completed child does not end the parent task.
